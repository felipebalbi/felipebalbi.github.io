Lambda in types, part 1: A perfectly good compiler, ruined

November 25, 2026 rust lambda-calculus type-system 7 min read

Rust’s type system spends most of its life preventing mistakes. I thought it deserved a change of pace, so I gave it a mistake to be.

We are going to implement lambda calculus in Rust types. Not a runtime interpreter written in Rust; that would be a sensible activity, and we have not gathered here for that. The expressions will be types. The results will be types. The compiler, which presumably had other plans, will do the work.

The original stretch goal was Conway’s Game of Life. The eventual finale is a little functional language that filters a list, squares its odd numbers, and adds them up. The answer is ten. We will spend sixteen weeks arranging for a compiler to discover ten. A seventeenth installment is a love-letter epilogue to Lisp, in case the parentheses hadn’t given us away. Please adjust your expectations accordingly.

There is no practical application. This is play. This week’s deliverable is that we can describe identity. We cannot evaluate it yet. Even by the standards of a project with no purpose, we are taking our time.

The rule of the experiment

There is a very easy way to cheat at this project. Make a Rust type called Add, give it an implementation that adds two Rust-level numbers, and call the result a language. That would get us to the wrong sort of bad idea.

Our self-imposed inconvenience is:

Rust supplies general evaluation rules. Lambda terms supply the programs.

Identity must be an expression in the language, not a special case in the evaluator. Later, the same restriction will apply to booleans, arithmetic, cells, and recursion. We may build human-facing output adapters, but those adapters must not secretly do the arithmetic we claim the language performed.

This is disposable code, not the beginning of a compiler framework. If I start discussing its enterprise plugin story, please take the keyboard away. We do need to be precise about which layer is doing what: being useless is a choice; being wrong would spoil the joke.

Three forms are enough to begin

Untyped lambda calculus gives us three expression forms:

FormWritten asWhat it describes
VariablexA reference to a bound argument
Abstractionλx. bodyA function with argument x and body body
Applicationfunction argumentApplying one expression to another

The dot separates a parameter from its body. Application associates to the left: f a b means (f a) b. A lambda’s body extends to the right unless parentheses say otherwise.[1]

The smallest example worth inflicting on a compiler is identity:

λx. x

It accepts an argument and gives that argument back. Functions can themselves be arguments, so this is a perfectly reasonable expression:

(λx. x) (λx. x)

Mathematically, applying the left-hand identity to the right-hand identity reduces to identity. That is an example of beta reduction, the rule that connects application to a function’s body. Today, the arrow is in our explanation, not in the Rust program:

(λx. x) (λx. x) → λx. x

Notice what the grammar doesn’t contain: no integer literals, no booleans, no lists, no named recursion. Those are not omissions we will patch by adding variants to a syntax enum. We will discover representations for them using the three forms we already have.

Names are pleasant until substitution gets involved

The names in λx. x are for us. Rename both occurrences to y and nothing changes: λy. y is the same function. The important fact is which binder owns which reference.

Here are two functions whose distinction does matter:

λx. λy. y    choose the inner argument
λx. λy. x    choose the outer argument

Keeping textual names would make us responsible for renaming variables carefully during substitution. In an open term, replacing a free x with y inside λy. x must not accidentally bind the new y. That is variable capture; the innocent-looking textual replacement changes the meaning.

We will use de Bruijn indices instead. A variable says how many binders outward to look, starting at zero:

λx. x       → λ. 0
λx. λy. y   → λ. λ. 0
λx. λy. x   → λ. λ. 1

The numbers are distances to binders, not the language’s future arithmetic values. 0 means “the nearest enclosing lambda’s argument.” 1 means “skip that binder and use the next.”[2]

This doesn’t make binding disappear. It makes the relationship explicit. Next week, our evaluator will still have to preserve that relationship when a function leaves the environment in which it was defined.

Put the syntax in types

Rust needs one constructor for each form:

use std::marker::PhantomData;

struct Z;
struct Var<N>(PhantomData<N>);
struct Lambda<Body>(PhantomData<Body>);
struct App<Function, Argument>(PhantomData<(Function, Argument)>);

Z is the index zero. That is the only index this snapshot needs; a way to represent larger indices arrives with nested evaluation in part 2.

Var<N> is a variable reference. Lambda<Body> contains the type describing a function body. App<Function, Argument> contains two type-level children. It records an application without performing it.

PhantomData is the standard marker for a relationship to a type without storing a value of that type. Rust requires us to use these generic parameters somehow; the marker makes the relationship explicit.[3] Our program constructs none of these structs at runtime. We only name the types.

Identity is now:

type Identity = Lambda<Var<Z>>;
type Expression = App<Identity, Identity>;

Read the first alias from the outside inward: a lambda whose body is a reference to its nearest argument. The second alias describes applying that expression to itself.

A type alias is not a new nominal type, a variable assignment, or a function call. Identity is another name for Lambda<Var<Z>>. Naming Expression does not cause a reduction. We have built the tree, not the machine that interprets it.

This separation is our first act of tidiness at the scene of the crime. If App<F, X> immediately meant “the result of calling F on X,” it would be much harder to talk about suspended work. Keeping application as syntax leaves that decision to the evaluator.

What can we run?

We can inspect the tree:

fn main() {
    println!("Identity: {}", std::any::type_name::<Identity>());
    println!("Application: {}", std::any::type_name::<Expression>());
}

Rust expands the aliases and usually includes module paths. Look for the shape Lambda<Var<Z>>, and for an App containing two copies of that shape. Do not treat the exact spelling as an output protocol. type_name is a diagnostic aid, not a stable serialization format, and certainly not proof that evaluation occurred.[4]

Nor have we built a well-scopedness checker. Rust lets us write Lambda<u8>, even though u8 is not one of our expression forms. We can also describe references with no matching binder once larger indices exist. Representation alone doesn’t establish validity. Later trait requirements will reject unsupported operations when evaluation demands them; that is not the same thing as checking every syntax tree up front.

Read and run this step

The source archive is the exact article-1 snapshot, afb9fbeb022c, not the final version of the experiment:

tar -xzf source.tar.gz
cd rust-lambda-types
cargo run --offline

Use a Rust toolchain supporting edition 2024. The archive has no third-party dependencies. Each later article includes its own snapshot, so following an early post does not require mentally deleting features introduced months after it.

Next week we will give the tree meaning. A lambda will become a closure, an argument will become suspended work, and application will connect the two. The first genuine result will still be identity. This time, Rust will have worked it out.
